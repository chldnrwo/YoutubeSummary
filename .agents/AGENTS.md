# YoutubeSummary 프로젝트 컨텍스트 및 에이전트 가이드라인

이 문서는 YoutubeSummary 프로젝트의 아키텍처와 핵심 설계 원칙을 담고 있습니다. 에이전트(Antigravity)는 프로젝트 환경을 분석할 때 반드시 이 문서를 숙지하고 지침을 따라야 합니다.

## 1. 프로젝트 개요
유튜브 영상을 요약하고, RAG 기반 챗봇 기능을 제공하며, 영상들에서 추출한 지식을 구조화하여 보여주는 **LLM 위키 시스템**을 포함한 Streamlit 기반 웹 애플리케이션입니다.

## 2. 핵심 아키텍처 & 설계 원칙
- **단일 파일 과부하 방지**: `app.py`가 이미 3,500줄 이상의 매우 큰 단일 파일로 구성되어 있습니다. 따라서 새로운 대형 기능(예: 위키 시스템)은 반드시 별도의 모듈(예: `wiki.py`)로 분리하여 개발합니다.
- **순환 참조(Circular Import) 엄격 금지**: 분리된 모듈(`wiki.py`)은 절대로 `app.py`를 `import` 해서는 안 됩니다. 데이터베이스 경로(`DB_PATH`), `user_id`, `api_key` 등 필요한 모든 값은 함수 호출 시 인자(Arguments)로 주입받아야 합니다.
- **데이터베이스 (SQLite)**: 
  - 기본 요약 데이터는 `insights` 테이블에 저장됩니다.
  - 기존 데이터를 보존하기 위해, 위키 관련 정보는 독립된 7개의 테이블(`wiki_entities`, `wiki_claims`, `wiki_entity_relations`, `wiki_insight_entities` 등)에 분리하여 저장합니다.
  - 추출 상태 관리를 위해 `insights` 테이블에 `wiki_extracted` (상태값: 1 성공, -1 실패, 0 미처리) 컬럼을 사용합니다.
- **트랜잭션 기반 상태 롤백**: LLM(Gemini) 추출 파이프라인 등 DB를 여러 단계로 수정하는 작업은 반드시 `sqlite3` 트랜잭션을 사용하여, 중간에 실패하더라도 상태가 깔끔하게 롤백되도록 해야 합니다.

## 3. LLM 위키 시스템 명세
위키 시스템은 영상의 요약 텍스트에서 '엔터티(인물/기업/주제)'와 '주장(Claim)'을 추출하여 다대다(N:M) 관계로 연결합니다.
- **추출 모델**: 빠르고 저렴한 `gemini-1.5-flash` (또는 `gemini-2.5-flash-lite`) 등의 경량 모델을 사용하여 백그라운드로 추출합니다.
- **주장(Claims)**: 단순 사실이 아닌 화자의 의견/예측을 강세(BULLISH)/약세(BEARISH)/중립(NEUTRAL) 논조와 함께 추출합니다.
- **엔터티 매칭**: 기존에 DB에 존재하는 엔터티와 유사한 이름이 나오면 새로 생성하지 않고 맵핑해야 합니다. (이름/별칭 정규화)
- **주식 종목 연동**: 기존 `stocks` 테이블의 주식 종목과 위키의 `COMPANY` 엔터티를 자동/수동으로 연결하여 시너지를 냅니다.

## 4. UI 개발 주의사항 (Streamlit)
- 동적 목록(리스트)을 렌더링하면서 `st.button`이나 `st.text_input`을 반복문 안에서 생성할 때는 **반드시 고유한(Unique) 키를 조합**해야 합니다. (예: DB ID + 인덱스 조합). 중복 키 에러(`StreamlitDuplicateElementKey`)가 발생하지 않도록 파이썬 레벨에서 먼저 중복을 제거(`set()` 활용)하는 방어 코드를 짜는 것이 좋습니다.

## 5. 글로벌 규칙
- 모든 코드 주석, 아티팩트, 시스템 프롬프트 작성 시 **사용자의 글로벌 규칙에 따라 반드시 "한국어"로 작성**해야 합니다.
